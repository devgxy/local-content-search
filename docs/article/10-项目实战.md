# 第 10 章 项目实战：本地混合检索

## 一句话结论

这个项目的价值不是“又一个 RAG demo”，而是把以下工程问题放进了同一条链路：

```text
多格式解析
→ 动态索引
→ 向量 + 关键词
→ scope
→ 重排
→ 表格/OCR
→ 评测
```

## 10.1 架构

```text
文件系统
  ↓
Manifest / 扫描
  ↓
Parser / OCR / 表格
  ↓
Chunk
  ↓
BGE Embedding
  ↓
LanceDB（向量 + FTS + 元数据）
  ↓
SearchService
  ├── vector
  ├── FTS
  ├── RRF
  └── rerank
  ↓
FastAPI
  ↓
Web UI
```

## 10.2 数据流

```text
scan
→ parse
→ chunk
→ embed
→ write new run
→ mark indexed
→ cleanup old
```

关键设计：

- `run_id` 隔离版本；
- 新版本成功后才切换；
- 删除文件清理旧 chunk；
- 失败文件显式记录；
- 不静默降级。

## 10.3 解析层

支持：

```text
MD / TXT / PDF / DOCX / PPTX
HTML / JSON / CSV / LOG
PNG / JPG
```

PDF：

- 文本层优先；
- 扫描页 OCR；
- bbox/阅读顺序；
- 页眉页脚；
- 表格。

图片：

- OCR；
- 表格检测；
- 单元格 OCR；
- 表格 HTML。

表格模型：

- 本地 Table Transformer；
- 默认关闭；
- 开启后加载检测/结构模型；
- 失败有 warning，不伪造成功。

## 10.4 Chunk 与索引

- 约 400 字符；
- overlap 50；
- max 600；
- 结构感知；
- 表格独立；
- 标题保留。

索引：

- LanceDB；
- 向量 1024 维；
- ICU FTS；
- `prefilter=True`。

## 10.5 检索策略

| 模式 | 行为 |
|---|---|
| `fts` | 关键词 |
| `vector` | 向量 |
| `hybrid` | RRF |
| `hybrid_rerank` | RRF + 重排 |
| `full` | 完整链路 |

`auto`：

```text
无 scope → full
有 scope → hybrid
```

原因：

- 全局检索需要更强排序；
- scoped 候选更集中，rerank 可能负收益。

## 10.6 当前指标

38 条简历 scoped：

| 配置 | Recall@5 | Recall@10 | MRR | nDCG | p50 |
|---|---:|---:|---:|---:|---:|
| hybrid | 0.6561 | 0.9518 | 0.6509 | 0.6974 | 30ms |
| full | 0.5684 | 0.9671 | 0.5349 | 0.6481 | 388ms |

这组数字说明：

```text
hybrid 的 MRR 更好；
full 的 Recall@10 略高，但前排排序更差。
```

小样本，不要过度解读。

## 10.9 失败复盘

### 失败 1：坏 PDF segfault

处理：

- 子进程隔离；
- `PARSER_CRASH`；
- 主进程继续；
- 原文件不变。

### 失败 2：表格 OCR 为空

处理：

- 保留原始 OCR 行；
- 只删除完整 cell 覆盖的行；
- 不生成空表冒充成功。

### 失败 3：rerank 负收益

处理：

- 固定候选 A/B；
- scoped 默认 hybrid；
- full 保留手动实验。

### 失败 4：full 延迟高

原因：

- 候选过多；
- 重排/上下文全量执行。

处理：

- 版本过滤后截断 top_k；
- p50 从 2721ms 降到 388ms。
