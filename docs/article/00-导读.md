# 第 0 章 导读：RAG 到底在解决什么

## 一句话结论

RAG 不是“让大模型记住更多”，而是：

```text
在生成答案之前，先把相关证据找出来。
```

它把“模型参数里的知识”换成“可更新、可追溯的外部资料”。

## 2. 术语约定

| 术语 | 含义 |
|---|---|
| RAG | Retrieval-Augmented Generation，检索增强生成 |
| Corpus | 语料库 |
| Query | 用户查询 |
| Document | 原始文档 |
| Chunk | 文档切片，检索基本单位 |
| Embedding | 文本向量 |
| Vector DB | 向量数据库 |
| FTS | Full-Text Search，全文检索 |
| Rerank | 对候选二次排序 |
| Ground Truth | 人工标注的标准答案 |
| Qrels | Query Relevance judgments，查询-相关性标注 |

评价指标缩写见第 8 章。

## 3. RAG 不是什么

### 不是“把文档塞进 prompt”

上下文窗口有限，成本高，且无法稳定处理大量文档。

### 不是“向量库一接就完事”

向量召回只是候选生成；后面还有：

```text
过滤 → 融合 → 重排 → 去重 → 截断 → 呈现
```

### 不是“模型回答得像”就对

RAG 需要：

- 检索到正确证据；
- 答案忠于证据；
- 引用可追溯；
- 找不到时能拒答。

## 4. 本文的项目边界

本文以一个本地混合检索工程为例：

- macOS 本地运行；
- LanceDB 向量 + 中文 FTS；
- BGE embedding + reranker；
- PDF/Office/图片 OCR；
- 文件/目录 scope；
- 可选表格结构模型；
- 本地 Web UI。

但文章不会把项目写成“唯一正确答案”。  
每一章都会区分：

```text
通用方案
本项目的选择
为什么这样选
什么时候不该这样选
```

---

## 5. 一条最重要的主线

```text
数据质量 → 切片质量 → 召回质量 → 排序质量 → 呈现质量 → 评测质量
```

任何一层坏了，后面的模型都很难补救。

下一章从全局链路开始。
