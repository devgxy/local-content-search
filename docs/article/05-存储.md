# 第 5 章 存储

## 一句话结论

RAG 的存储不只是“存向量”，而是同时解决：

```text
向量相似度
关键词检索
元数据过滤
版本与删除
```

## 5.1 一个 chunk 存什么

```text
chunk_id
doc_id
chunk_index
text
vector
heading
page / slide
file_name / file_path
source_kind
meta_json
run_id
```

术语：

| 术语 | 解释 |
|---|---|
| Schema | 表结构 |
| Primary Key | 主键 |
| Metadata | 元数据 |
| Columnar Storage | 列式存储 |
| Scalar Index | 标量索引 |

## 5.2 向量索引

| 索引 | 特点 |
|---|---|
| Flat | 暴力扫描，最准最慢 |
| HNSW | 图索引，查询快，内存高 |
| IVF | 聚类倒排，适合大规模 |
| PQ | 乘积量化，压缩向量，损失精度 |

术语：

| 术语 | 解释 |
|---|---|
| ANN | 近似最近邻 |
| Recall@K | 近似索引找回真实最近邻的比例 |
| Prefilter | 先过滤再检索 |
| Postfilter | 先检索再过滤 |

## 5.3 全文检索

关键词检索解决：

- 专有名词；
- 编号；
- 人名；
- 代码符号；
- 向量不敏感的字面匹配。

术语：

| 术语 | 解释 |
|---|---|
| FTS | Full-Text Search，全文检索 |
| BM25 | 经典关键词相关性算法 |
| Tokenizer | 分词器 |
| ICU | International Components for Unicode，中文分词库 |
| Inverted Index | 倒排索引 |

## 5.4 混合存储

本项目：

```text
LanceDB：向量 + 标量 + FTS
SQLite Manifest：文件清单/状态/版本
```

为什么不用两个独立数据库：

- 同一个 chunk 的向量和文本要一起过滤；
- 版本切换要一致；
- 删除要同时清理；
- 少一个同步故障点。

## 5.5 版本模型

动态文档必须有：

```text
doc_id
run_id
content_hash
status
```

术语：

| 术语 | 解释 |
|---|---|
| Run | 一次索引构建 |
| Atomic Switch | 原子切换 |
| Tombstone | 删除标记 |
| Rollback | 回滚 |
| Manifest | 文件清单 |

流程：

```text
写新 run
→ 校验
→ 切换 manifest
→ 清理旧 run
```

不要先删旧版本。

## 5.6 过滤

常见过滤：

- 文件类型；
- 目录/根；
- doc_id；
- 时间；
- 权限。

```text
prefilter：先按元数据缩小范围，再向量检索
postfilter：先向量检索，再过滤
```

权限场景必须 prefilter，避免候选泄露和结果不足。

## 5.7 备份与恢复

需要备份：

```text
LanceDB 目录
Manifest
配置
```

不需要备份：

```text
可重新下载的模型
可重新生成的缓存
```

恢复后要校验：

- schema 维度；
- 文件状态；
- FTS 索引；
- 向量索引；
- 版本一致性。

## 5.8 检查清单

- [ ] schema 是否包含 doc/chunk/run？
- [ ] 是否有 FTS 和向量索引？
- [ ] 过滤是否 prefilter？
- [ ] 删除是否清 chunk/asset？
- [ ] 是否原子切换？
- [ ] 是否有备份/恢复流程？
