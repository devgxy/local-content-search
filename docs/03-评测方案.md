> 用途：定义“怎么证明这套系统真的比纯向量好”，包括数据集、指标、实验协议、验收阈值与报告模板。

---

## 1. 评测目标

1. 验证混合检索（向量 + FTS + RRF）是否优于单路召回；
2. 验证 `bge-reranker-large` 是否在 Top-K 上带来稳定增益；
3. 量化延迟，确认桌面交互可接受；
4. 建立回归基线，防止后续改切片/模型/参数时效果回退；
5. 暴露失败类型（OCR 噪声、切片边界、重复结果、中文分词）。

> 评测不是“跑一个数字”，而是每次改动后能回答：**变好了还是变差了，差在哪。**

## 2. 数据集设计

### 2.1 双层策略

| 层级 | 数据集 | 作用 | 规模 |
|---|---|---|---|
| L1 真实场景 | 用户 Downloads 样本 | 判断“对我有没有用” | 100–300 文档，30–50 query |
| L2 公开基准 | 中文检索公开集子集 | 判断“方法是否普遍有效” | 5k–20k passages，100–300 query |

L1 是主评测，L2 是辅助与对外可复现性。两者都只在本机运行，不上传任何数据。

### 2.2 L1：Downloads 样本集

**语料选择**

- 只扫描用户明确允许的目录；
- 优先选取 PDF/DOCX/PPTX/图片，保证覆盖十类格式；
- 单文件 < 50MB，避免评测被大文件主导；
- 抽样 100–300 个文档，记录 `manifest` 快照（路径、大小、mtime、doc_hash）；
- 语料快照写入 `data/eval/personal/corpus.json`（gitignore）。

**Query 构造**

没有现成 query 时，采用“人工阅读 + 结构化模板”，不依赖 LLM：

| 类型 | 占比 | 构造方法 | 示例 |
|---|---|---|---|
| 语义型 | 40% | 读一段正文，用自己的话描述需求，避免复述原词 | “那份讲本地模型内存占用的材料” |
| 关键词型 | 30% | 错误码、人名、产品名、专有名词 | “E1024 连接超时” |
| 混合型 | 30% | 一个关键词 + 一个语义描述 | “PPT 里讲的 RRF 融合怎么做” |

**约束**

- 禁止直接用文件名/标题作为 query（否则等于测文件名检索）；
- 每条 query 标注 1–3 个相关文档（doc 级，二值或三级）；
- 覆盖至少 20% 的 OCR-only 内容（扫描 PDF/图片）；
- 覆盖至少 3 种文件类型；
- 由同一人构造并复核，避免“看着答案出题”。

**格式（JSONL）**

```jsonl
{"qid":"p001","query":"本地部署重排模型内存占用多大","relevant":["/Users/example/Downloads/a.pdf"],"grade":[2],"type":"semantic","note":"第 3 页"}
{"qid":"p002","query":"错误码 E1024 怎么解决","relevant":["/Users/example/Downloads/manual.docx"],"grade":[2],"type":"keyword","note":"表格中"}
```

- `relevant` 用绝对路径，评测时映射到 `doc_id`；
- `grade` 可选：2=高度相关，1=部分相关；缺省按 1 处理；
- `type` 用于分桶统计。

当前已落地：

- `examples/eval-resume-38.jsonl`：38 条简历 query；
- `examples/eval-resume-tables-6.jsonl`：6 条表格内容 query；
- `examples/eval-resume-chunks-10.jsonl`：10 条 chunk 级 query；
- `examples/eval-resume-anchors-10.jsonl`：10 条 query / 29 个内容锚点；
- `examples/eval-multi-root-8.jsonl`：8 条多根 query；
- `data/eval/public/t2retrieval/queries.jsonl`：T2Retrieval 子集；
- `examples/eval-docs-md-10.jsonl`：项目 docs Markdown 动态 scope；
- `examples/eval-docs-pdf-10.jsonl`：同一内容的合成 PDF 动态 scope；
- `examples/eval-resume-candidates-10.jsonl`：41 份简历 PDF 的候选人筛选。

> chunk 级 `path#chunk_index` 标签绑定固定快照；
> 动态/重建场景用 `relevant_anchors`（path + quote + heading/doc_hash），
> 并用 `--root-path` 只评测选中的索引根。
> 锚点解析失败会报告 `anchor_missing`，不会静默算错。
>
> 动态选文件支持 `scope_doc_ids` / `scope_file_paths`，检索时走 LanceDB prefilter；
> parent/child rerank 通过 `RERANK_PARENT_CONTEXT=true` 可选开启，默认关闭。
- 默认评测口径：`top_k=20`、`final_k=5`；
- 默认检索模式：`auto`；无 scope 用 `full`，有 scope 用 `hybrid`；手动可选 `full/hybrid`。

### 2.3 L2：公开中文检索集

**首选：T2Retrieval（C-MTEB / MTEb）**

- 中文段落检索，含 queries / corpus / qrels；
- 体量较大，评测时抽样：5k–20k passages + 100–300 queries；
- 通过 `hf-mirror` 或 ModelScope 下载，转换成本地方便的 JSONL；
- 需检查许可证，仅本地评测使用。

**备选：**

| 数据集 | 说明 | 适用 |
|---|---|---|
| MMarco-zh | 中文 MS MARCO，体量大 | 抽样后可用 |
| DuReader-retrieval | 中文问答式检索 | 备选 |
| BeIR（英文） | 英文基准 | 仅验证通用性，不作主指标 |

**统一格式**


2. 抽样 corpus 与 queries；

4. 写入上述三个文件；
5. 记录抽样种子与原始版本号。

> 公开集只用于“方法对比”，不参与调参后的再次挑选；避免过拟合。

## 3. 指标定义

设某条 query 的相关文档集合为 \(R\)，系统返回前 \(k\) 个**去重后的文档**为 \(T_k\)。

| 指标 | 定义 | 说明 |
|---|---|---|
| `Recall@k` | \(|R \cap T_k| / |R|\) | 主指标；衡量“找没找到” |
| `MRR@10` | \(1/rank_{first}\)，无则 0 | 衡量“第一条多快出现” |
| `nDCG@10` | \(\sum (2^{g_i}-1)/\log_2(i+1)\) 归一化 | 支持分级相关 |
| `ZeroResultRate` | 空结果 query 占比 | 鲁棒性 |
| `DocDupRate@5` | Top5 中重复文档占比 | 去重效果 |
| `p50/p95 latency` | 端到端毫秒 | 交互体验 |
| `OCRRecall@10` | OCR-only query 的 Recall@10 | 图片/扫描件覆盖 |

**文档级聚合规则：**

- 一个文档可能命中多个 chunk；指标按文档去重后计算；
- 文档得分取该文档最高分 chunk；
- 这样避免“同一文档多 chunk 刷榜”。

## 4. 实验配置

| 配置 | 向量腿 | FTS 腿 | 融合 | 重排 | 去重/上下文 |
|---|---|---|---|---|---|
| C1 `vector` | ✅ | ❌ | — | ❌ | ❌ |
| C2 `fts` | ❌ | ✅ | — | ❌ | ❌ |
| C3 `hybrid` | ✅ | ✅ | RRF | ❌ | ❌ |
| C4 `hybrid_rerank` | ✅ | ✅ | RRF | ✅ | ❌ |
| C5 `full` | ✅ | ✅ | RRF | ✅ | ✅ |

- 主对比：C1 / C3 / C4 / C5；
- C2 用于验证关键词场景；
- 所有配置共用同一份切片与同一 `top_k`（默认 20），C4/C5 的 `final_k=5`；
- 重排候选数固定，避免“多取候选”带来的不公平优势。

## 5. 实验协议

### 5.1 环境固定

- 同一台机器（M5 Max / 64GB）；
- 同一模型版本与路径（记录 SHA256 或文件大小）；
- 同一 LanceDB 版本（0.40.0）；
- 同一 chunk 参数（400/50）；
- 关闭其他占用 GPU 的应用；
- 记录 `git` 状态或代码版本号。

### 5.2 流程

1. 建立评测语料快照，生成 `corpus.json`；
2. 全量入库，记录 `chunks` 数与构建耗时；
3. 预热：跑 3 条与评测无关的 query；
4. 对每个配置，逐条 query 执行 3 次，取中位数；
5. 记录 Top-10 文档与分数；
6. 计算指标；
7. 生成报告；
8. 对失败 query 做人工归因（每配置至少 5 条）。

### 5.3 防泄漏

- Query 不得由被测系统生成；
- 构造 query 的人不看检索结果；
- 调参使用开发集（前 50% query），报告使用留出集（后 50%）；
- 公开集只做最终对比，不反复调参。

### 5.4 延迟测量

- 端到端：从 API 收到请求到返回 JSON；
- 分解：query 编码、LanceDB 检索、重排、后处理；
- 预热后测量；报告 p50/p95；
- 不把首次冷启动混入热态指标，单独报告“首查延迟”。

## 6. 验收阈值（初版，待基线校准）

| 指标 | 目标 | 说明 |
|---|---|---|
| L1 Recall@10（C5） | ≥ 0.80 | 主指标 |
| L1 nDCG@10（C4 vs C3） | 相对 +10%，至少不低于 -2% | 证明重排价值 |
| L1 关键词子集 Recall@20（C3） | ≥ 0.90 | 证明 FTS 价值 |
| L1 ZeroResultRate | ≤ 5% | 鲁棒性 |
| L1 p95 latency（C5） | ≤ 1.5s | 桌面体验 |
| L2 Recall@10（C5） | 不低于同规模基线 | 方法有效性 |
| OCR 子集 Recall@10 | ≥ 0.70 | 图片/扫描件可接受 |

> 若首轮基线低于阈值，不直接判失败：先看失败归因，再决定是调切片、调 top_k、换 reranker base，还是接受现状并记录。

---

## 7. 失败归因分类

| 类别 | 判定 | 可能原因 | 处理 |
|---|---|---|---|
| `MISS_PARSE` | 正文没进库 | 解析失败/加密/图片未 OCR | 看 manifest 错误、补 OCR |
| `MISS_CHUNK` | 正文在库但切片切断 | 切片边界/标题前缀 | 调 chunk_size/overlap |
| `MISS_EMBED` | 语义相近但未召回 | 查询指令/模型能力 | 加 instruction、换模型 |
| `MISS_FTS` | 关键词未命中 | 分词/大小写/符号 | ICU 参数、query 规范化 |
| `RERANK_DROP` | 召回有但重排排到后面 | 切片过长/噪声 | 缩短切片、限制候选 |
| `DUP_DOC` | Top5 同一文档 | 无去重 | per_doc_limit / MMR |
| `OCR_NOISE` | OCR 文本错字 | 图片质量 | 置信度过滤、原图提示 |

每条失败 query 在报告中记录：query、期望文档、实际 Top5、归因、建议。

## 11. 风险与注意事项

| 风险 | 影响 | 对策 |
|---|---|---|
| 样本量小（30–50 query） | 指标波动大 | 报告置信区间；分桶看趋势；不追求小数点后两位 |
| Query 与语料同源 | 过拟合 | 留出集；禁止用标题原词 |
| OCR 噪声 | 图片类指标偏低 | 单独分桶；记录 OCR 置信度 |
| 公开集过大 | 下载/入库耗时 | 抽样 5k–20k；固定种子 |
| 公开集许可证 | 合规 | 仅本地评测；不随仓库分发 |
| 延迟受后台任务干扰 | 数据不稳 | 评测前停止同步任务；单进程 |
| 重排收益被 top_k 放大 | 不公平 | 所有配置统一候选数 |

## 12. 与步骤的关系

- STEP-07 完成后即可跑 C1–C4 的冒烟评测；
- STEP-10 负责正式数据集、指标实现、报告与失败归因；
- STEP-11 把“评测通过”作为交付门槛之一；
- 后续任何改动（切片、模型、FTS 参数）都必须附一份新报告。
